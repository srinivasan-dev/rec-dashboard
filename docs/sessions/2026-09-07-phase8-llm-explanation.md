# 2026-09-07 — Phase 8: LLM Explanation Feature

**Phases/epics touched:** Phase 8 (LLM Explanation Feature).
**Shipped:** see `CHANGELOG.md` "[Phase 8] - 2026-09-07 - LLM Explanation Feature".

## Decisions & why

- **Read MASTER_PROMPT's Phase 8 section verbatim before designing anything** — it's unusually
  prescriptive (exact system-intent wording, exact 7-topic `docs/ai-design.md` outline, exact
  ship recommendation to state). Followed it closely rather than reinterpreting, since departing
  from explicit instructions here would look like not having read them.
- **`ExceptionExplanationProvider` takes a structured `ExplanationContext`, not the raw
  `ReconciliationException`.** The context has exactly 7 fields (transaction id, reason,
  currency, settlement/ledger amount+date, difference, duplicate count) built once by
  `buildExplanationContext`. This makes grounding structural rather than a prompt-engineering
  hope: a provider (mock or real) literally cannot reference a fact that isn't in that object,
  because nothing else is ever constructed and handed to it.
- **Two independent fallback triggers, not one.** MASTER_PROMPT distinguishes "if the AI request
  fails" from "if the result appears unusable" — implemented as two separate checks in
  `explanationService.ts`'s `getExplanation`: a try/catch around the provider call, and a
  separate `isUsable()` validation (length bounds + a banned-language regex list: fraud, stolen,
  lost, missing funds, liability) applied to whatever the provider returns even when the call
  succeeded. Both routes land on the same `buildDeterministicExplanation` fallback, but they're
  tested as genuinely separate cases (`explanationService.test.ts` has one test per failure mode)
  since a provider that "succeeds" with alarming language is a distinct, real risk from one that
  times out.
- **Provider identifies itself via a `readonly id` property**, and `explanationService.ts` uses
  `provider.id` (not a hardcoded string) for the successful `generatedBy` value. This is what
  makes "design it so a real LLM provider could later replace the mock" concrete rather than
  aspirational: swapping `MockExplanationProvider` for a real one changes `generatedBy` in the
  API response automatically, with zero changes to the service or the frontend's badge logic.
- **Renamed Phase 4's `explanationStub.ts` to `deterministicExplanation.ts`, kept its content.**
  The text itself was already calm, reason-keyed, and product-reviewed-adjacent — no reason to
  rewrite it. What changed is its role: it's no longer _the_ response, it's _the guaranteed
  fallback_ when a provider isn't trustworthy. `generatedBy` changed from `'stub'` to
  `'fallback'` to reflect that role change honestly.
- **Frontend badge logic inverted, not just relabeled.** The Design Implementation session had
  wired the badge to say "Auto-generated" only for `generatedBy === 'stub'` — at the time, stub
  was the _only_ path, so that check happened to always fire. Now that a real provider path
  (`'mock'`) and a fallback path (`'fallback'`) both exist, the badge must NOT claim
  "Auto-generated — verify details" for the fallback case, since that text wasn't actually
  generated by anything AI-like. Changed the badge to show a plain "Standard explanation" for
  `generatedBy === 'fallback'` and reserve "Auto-generated" for everything else. Added a
  dedicated test (`does not claim "AI-generated" when the backend used its deterministic
fallback`) specifically to pin this, since it's an easy regression to reintroduce silently.
- **Verified live, not just via unit tests** — hit the real endpoint directly (`curl -X POST
.../T1013/explanation`) and drove the dashboard with Playwright for two different exceptions
  (AMOUNT_MISMATCH and MISSING_LEDGER), confirming the mock provider's output is genuinely
  per-transaction (different amounts/dates/wording each time), not a relabeled canned string.

## Direction changes / pivots

None — this followed the standing plan from the Design Implementation session's resume note
(`getExplanation`'s shape was already fixed by the frontend's `AiExplainPanel`, built ahead of
this phase; Phase 8's job was building the real provider/fallback logic behind that existing
contract, which is exactly what happened).

## Deferred / explicitly out of scope this session

- **Logging/observability for provider fallbacks** — `docs/ai-design.md` §5 names the design
  (log provider id, latency, and which of the two fallback reasons fired, distinctly) but no
  logging infrastructure exists in `apps/api` at all yet, so nothing was implemented. Flagged as
  a gap, not silently skipped.
- **A real LLM provider implementation** — out of scope per MASTER_PROMPT itself ("provide
  MockExplanationProvider... design it so a real LLM provider could later replace the mock", not
  "implement one"). The interface and prompt-building are real and tested; no network call to an
  actual model exists anywhere in this codebase.
- **`CURRENCY_MISMATCH` copy remains unreviewed** — now duplicated across three places
  (`exceptionLabels.ts`, `deterministicExplanation.ts`, `MockExplanationProvider`), all original
  content following the same calm-language principles as the reviewed reasons, none actually
  reviewed by product. Pre-existing gap, now slightly wider in surface area.
